## 前文(Foreword)の日本語訳

ドローンはニュージーランドで羊の誘導に使われ、牧羊犬を空飛ぶ機械に置き換えた。日本ではオフィスビルが大音量の音楽とライトを放つドローンを飛ばし、働きすぎの社員を文字通り追い立てて家に帰らせている。壁面にグラフィティを描くよう訓練されたドローンもあり、テクノロジーとストリートアートが反骨精神で融合した例だ。スウェーデンでは、絶滅危惧種を研究するために海面に浮かぶクジラの糞を探知するドローンが使われた。鳥や昆虫の形をした実験的なドローンは、気づかれずに偵察するために羽ばたきながら飛ぶ。プロペラを使わず、シャボン玉を羽ばたかせて飛ぶドローンさえ存在する。火山研究では、あるドローンが噴煙の中に突入し、空中で溶けてしまったが、消滅する数秒前にデータを送り返すことに成功した。そして韓国では、同期制御されたドローンショーが花火に取って代わり、より安全で静かで、なぜか一層魔法のような光景を生み出している。

「車輪の再発明」という言い回しは、車輪がずっと昔からある優れた発明であり、非常によく機能しているという発想に由来する。特に問題がないのだから、それをもう一度発明し直しても大して役に立たず、むしろ時間の無駄になりかねない――特にその時間を新しい問題の解決に充てられるのであれば、なおさらだ。

プログラミングにおいてこれが起こるのは、すでに存在するものをゼロから作ってしまう場合だ――たとえば、堅牢なオープンソース版が既に存在するのに、自前でソートアルゴリズムやフレームワークを書いてしまうようなケースである。ただし、それが完全に悪いというわけではない。自分の手で作ってみることは、物事が内部でどう動いているかを学ぶ良い方法にもなり得る。重要なのはバランスを見つけることだ――すべてを再構築する必要はないが、自分が使っているツールが実際にどう動いているかを探る時間は取るべきである。そうすることで、同じ「車輪」を作り直すことに囚われず、開発者として成長できる。

## 課題要件のまとめ

### 概要
- 課題名: Fly-in(42カリキュラム、v1.6)
- 目的: 複数のドローンを開始ゾーン(start)から終了ゾーン(end)へ、制約下でシミュレーションターン数を最小化しつつ移動させるルーティングシステムをPythonで設計する。

### AI利用方針(章II)
- AIは反復・退屈な作業の削減に使ってよいが、生成された内容は完全に理解し、自分の責任で説明できるものだけ使用すること。
- 必ずピアレビューを受けること(自己検証のみに頼らない)。
- 丸ごとコピペして中身を説明できない状態は「悪い実践」として明記されている(評価で失格になりうる)。
- → 本プロジェクトで「指示があるまでコードに触らない」という運用方針(`CLAUDE.md`)の根拠。

### 共通ルール(章III)
- Python 3.10以上、flake8準拠必須。
- 例外処理は try-except で丁寧に。ファイル等のリソースは context manager で管理。
- 型ヒント必須、mypyで静的型チェックをパスすること。
- 関数・クラスにPEP 257準拠のdocstring。
- Makefile必須: `install` / `run` / `debug`(pdb使用) / `clean` / `lint`(flake8 + mypy 指定オプション) / `lint-strict`(任意、mypy --strict)。
- テストコード(pytest/unittest)は作成推奨だが提出・採点対象外。
- `.gitignore` 必須。仮想環境使用推奨。

### 制約(章V) — 特に重要
- グラフ処理系ライブラリの使用禁止(networkx, graphlib等)→ グラフ構造・探索アルゴリズムは自作必須。
- 完全に型安全であること(flake8 + mypy必須)。
- 完全にオブジェクト指向であること。→ ピアレビューで実証を求められる。

### 入力フォーマット(章VI)
- 1行目: `nb_drones: <数>`
- ゾーン定義: `start_hub:` / `end_hub:` / `hub:` の各行に `<name> <x> <y> [metadata]`
- メタデータ(角括弧、順不同、省略可):
  - `zone=<type>`(既定 normal)
  - `color=<value>`(既定 none、任意の1語文字列)
  - `max_drones=<N>`(既定1)
- ゾーンタイプ:
  - `normal`: 移動コスト1ターン(既定)
  - `blocked`: 侵入不可(通過する経路は無効)
  - `restricted`: 移動に2ターンかかる
  - `priority`: コスト1ターンだが経路探索で優先されるべき
- 接続: `connection: <name1>-<name2> [max_link_capacity=<N>]`(既定1、双方向)
  - ゾーン名にダッシュ・スペース不可
- `#` から始まる行はコメント
- 座標は常に整数、start/endは必ず一意に1つずつ存在

### パーサ制約(章VII.4)
- `nb_drones` は正の整数。任意の数のドローンに対応すること。
- start_hub / end_hub はそれぞれちょうど1つ。
- ゾーン名は一意、接続は既定義ゾーン間のみ、重複接続禁止(a-b と b-a は同一とみなす)。
- 不正なゾーンタイプ・不正なメタデータはパースエラー。
- 容量値(max_drones, max_link_capacity)は正の整数。
- start_hub / end_hub には max_drones の容量制限は適用されない(指定されていても無視、エラーにしない)。
- その他のパースエラーは行番号と原因を明示して停止すること。

### ゾーン占有ルール(章VII.2)
- 既定では1ゾーンにつき同時1ドローンまで。`max_drones=N` で緩和可能。
- 例外: start(全ドローンが初期共存可)、end(到着後は配達完了扱いで無制限)。
- 同一ターンに同一ゾーンへ、容量を超えて複数ドローンが入ることは不可。
- `max_link_capacity` は接続(エッジ)を同時に通過できるドローン数の上限。

### 移動・ターンの仕組み(章VII.3)
- 各ターンで各ドローンは: 隣接ゾーンへ移動(容量が許せば) / restrictedゾーンへの移動を開始(要2ターン、開始したら次ターンで必ず到着、経路上で待機不可) / その場に待機、のいずれかを行う。
- 移動元ゾーンの容量はそのターン中に空く(同時に出て入れる)。
- 移動コスト: normal=1, restricted=2, priority=1(ただし優先すべき), blocked=侵入不可。

### 出力フォーマット(章VII.5)
- 1ターン=1行。その行に、そのターンに動いたドローンの `D<ID>-<zone>` (または飛行中の `D<ID>-<connection>`) をスペース区切りで列挙。
- 動かなかったドローンはその行に書かない。
- 終了ゾーン到達後のドローンは「配達済み」として以降追跡しない。
- 全ドローンが到達したらシミュレーション終了。

### スコアリング(章VII.6)
- 主評価: 全ドローンが到達するまでの総ターン数(少ないほど良い)。
- 有効なシミュレーションの条件: 移動・占有ルール遵守、ゾーンタイプ別コストの正しい処理、容量制約遵守、衝突なし。
- 副次指標(任意): ターンあたりの移動ドローン数、ドローン平均ターン数、総経路コスト、可視化の質。同ターン数なら副次指標やコード品質で比較。

### パフォーマンス目標(章VII.7、任意=成績に直結しないが評価される)
- Easy: 10ターン未満(linear path 2機≤6, simple fork 4機≤8, basic capacity 4機≤6)
- Medium: 10〜30ターン(dead end trap 5機≤12, circular loop 6機≤15, priority puzzle 5機≤12)
- Hard: 60ターン未満(maze nightmare 8機≤30, capacity hell 12機≤35, ultimate challenge 15機≤45)
- Challenger(任意・成績非対象): The Impossible Dream 25機、参考記録45ターンを更新できれば優秀
