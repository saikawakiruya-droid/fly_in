# Scheduler の判断の順序を「ドローン単位」から「ゾーン単位」に変えた試作

- 日付: 2026-10-19
- 対象: develop(c9202ed)の `Scheduler`(`droneflow/simulation/scheduler.py`)
- きっかけ: ユーザーの想定は「ゾーンを順に確認し、そのゾーンにいる動かせるドローンを動かす」で、ドローン ID を順序に使うことは
  想定していなかった。また、確認の順番には start からの距離を参考にするつもりだった(記録には残っていなかった)。
- 方法: リポジトリ外の使い捨てスクリプトで `Scheduler._decision_order` だけを差し替え、他(予約表・立ち退き・`next_hops`)は
  そのままにして比較した。コードは変更していない。

## 比べた順序

| 名前 | 並べ方 |
|---|---|
| 現状 | ドローン単位: end までの距離 → 優先ルート上を先 → ドローン ID |
| zone(dist,prio,decl) | ゾーン単位: end までの距離 → 優先ルート上を先 → ゾーンの宣言順。ゾーン内のドローンはまとめて判断 |
| zone(dist,prio,start±) | 上の宣言順の前に start からの距離(+ は近い順、- は遠い順)を入れる |
| zone(dist,start±) | 優先ルートを使わず、end までの距離 → start からの距離 → 宣言順 |

ゾーン内のドローンの並びは `active_drones()` の並び(結果として ID 順)だが、同じゾーンのドローンは選べる手が同じなので、
入れ替えてもターン数は変わらない。

## 結果

### 配布マップ10枚・課題の例・revie_case(25枚)

すべての順序で、**ターン数もターンログも完全に一致**した。判断の順序そのものが現状と違ったターンも0だった
(end までの距離が同じ複数のゾーンに、ID の順が入れ違いになる形でドローンがいる場面が、これらのマップでは起きない)。

### ランダムなマップ

| マップの集合 | 枚数 | 現状の合計ターン | zone(dist,prio,*) | zone(dist,start±) |
|---|---|---|---|---|
| 層状(隣の層とだけ接続) | 3000 | 33925 | 34049(良 28 / 悪 83) | 34065(良 41 / 悪 106) |
| 層を飛ばす接続あり | 1871 | 18507 | 18526(良 11 / 悪 22) | 18528(良 16 / 悪 28) |

(良/悪 = 現状よりターン数が少ない/多いマップの数。1枚あたりの差は最大で ±4〜6 ターン)

- ゾーン単位にすると、わずかに悪くなる方向。
- start からの距離を近い順・遠い順のどちらで入れても、宣言順と**完全に同じ結果**になった
  (ゾーンの並びが変わったマップは1753枚あったが、ターンログが変わったものは0枚)。

## 分析

### start からの距離が効かない理由

ドローンは `next_hops`(最短のまま goal に進める一手)しか通らない(立ち退きも同じ)。そのため、ドローンがいられるゾーンは
すべて start→end の最短経路上にあり、そこでは `start からの距離 = dist(start) − end までの距離` が必ず成り立つ。
end までの距離で並べた後に start からの距離を比べても、同じ距離の中では値がすべて同じで、順序を決める情報にならない。

### ゾーン単位が悪くなる例(r00054、現状9 → ゾーン単位10)

ターン4で、end までの距離が同じ3つのゾーンにドローンがいた: z0_0 に D7、z0_1 に D8、z0_2 に D6。

- z0_2 からの最短の一手は z1_0 だけ。z0_0 からは z1_0 と z1_1 の2つ。
- 宣言順(z0_0 が先)では、選択肢が2つある D7 が先に z1_0 の最後の空きを取り、選択肢が1つしかない D6 が待たされた。
- ID 順では D6 が先に z1_0 に入り、D7 は z1_1 に回れた。

ID の小さいドローンは先に出発しているため、ID 順は「長く待っている機から」に近い。この例では、たまたまそれが
「選択肢の少ない機から」と一致して有利になった。ID 順もゾーンの宣言順も、この観点では原理的な基準ではない。
