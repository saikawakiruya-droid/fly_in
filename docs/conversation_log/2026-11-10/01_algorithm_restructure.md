## 質問: 「先に進む道を決めて、ゴールに近いドローンから動かす」はダイクストラ法か

- 回答: 二つの部分に分かれる。道を決める部分は最短経路探索(ダイクストラでできる)。近いドローンから動かす部分は
  ダイクストラではなく、動かす順番の決まり(優先度の規則)
- 今のコードとの違い: 今も距離はダイクストラ(DistanceMap)で、決める順番もゴールに近い順(ZoneRanking)。
  違いは、道を最初に決めず、毎ターン次の一手だけを選んでいること
- 注意点: 全機が同じ最短経路を取ると渋滞する。道を決めるときに、先に決めた機体の分を考えて散らす必要がある
  (例: 使われた経路に重みを足してから次の機体の経路を探す)
- 未決: 道を散らす方法、待つかどうかの決め方

## 質問: 最初に全機を探索的に進め、衝突したルートは分岐元まで消して、移動用のマップを持てば、移動中は確認だけにできるか

- 回答: できる。最初に全ターンの計画を作り、シミュレーション中はそれを読んで TurnResolver で確かめるだけにする形
- ただし「衝突したルートを分岐元まで消す」は勧めない。衝突は時刻で決まる(同じゾーンでも1ターンずらせば通れる)ので、
  道ごと消すと使える道まで捨てる。分岐元まで戻るやり直しは、機体が増えると組み合わせが爆発する
- 代わりの案: 1機ずつ順に、(ゾーン, ターン) を単位にした予約表を避けて経路を探す(「待つ」も一手に入れる)。
  先に決めた機体の予約は動かさないので、やり直しが要らない。スタートは容量無制限なので、待てば必ず道が見つかる
  (一般に prioritized planning / 時間を足したグラフでの最短経路探索と呼ばれる)
- 未決: この方式で進めるか、機体を決める順番

## ユーザーの考え: 欲しいのは常に渋滞せずに進めるルート。わかれば最短に収束するはず

- 回答: 考え方は正しい。最小費用流で容量を守る経路の組と毎ターンの台数を求め、毎ターン繰り返す方法
  (temporally repeated flow)は、スタート・ゴールが1つのとき最適。ただし最短1本に収束するのは台数が少ないときだけ
- 調査記録: `docs/research/2026-11-10_congestion-free-flow.md`
- 未決: この方式で作り直すか、priority の扱い

## ユーザーの方針: 計画の順番はゾーン単位でゴールに近い方から見て、空いているゾーンは手前から機体を持ってくる(引き込み)

- 回答: 1ターン内の動かし方として合っている。近い方から見るので空いた席が先にわかり、空いている所にしか入れないので
  追い出しが要らない(今の ZoneRanking の順番と同じ考え方)
- 引き込みだけで足りない点: どの手前のゾーンから持ってくるか、遠回りの経路にいつまで流すかが決まらない。
  空いていればいつでも引き込むと、長すぎる経路(l_i > T)にも流れて全体が遅くなる
- 提案: 引き込める辺を最小費用流で使う辺に限り、各経路はスタートから T − l_i + 1 ターン目まで流す。
  流れが容量を守るので、引き込みは常に成功し、実行時は確認だけになる
- 未決: 引き込みと流れを組み合わせるか、手前のゾーンが複数あるときにどれから持ってくるか

## 質問: 満員のゾーンはできるか(常に一方向に進み、決める順番で防げるはず)

- 回答: 「動けなくなる詰まり(デッドロック)」と「追い出しが要る状況」はできない。一方向に進み、前から決めるので、
  空いた席が先にわかるため。ただし「容量いっぱいのゾーン」自体はボトルネックの手前にできる
  (例: start → A(容量2) → B(容量1) → end。A は毎ターン1台出て1台入り、2台のまま。止まりはしないが、待ちの列)
- この待ちは害がない。問題になるのは、遠回りを使えば早く終わる台数のときに、待ちの列ができること(流れで決める部分)
- 確認: 「遠いところから動かす」は、ゴールに近い側からの意味か。文字どおり遠い側からだと、前が抜ける前に後ろを決めるので
  空き席が見えず、余計に待つ

## ユーザーの考え: 長さ l_i が T を超える道は、前と同じやり方でよい

- 解釈(確認中): 前と同じやり方 = 今の DetourPolicy の判定
  (`cost(v)+dist(v)+queue(v) <= dist(u)+ahead(u)`、遠回りしても最短の列に並ぶより遅くならないときだけ入る)
- 回答: それでよい。この判定は「l_i ≤ T の道だけ使う」をその場で見積もる版。最小費用流を作らずに済む。最適の保証はない
- 引き込み方式に入れるときの確認点:
  1. ahead(u) は台数をそのまま足していて、容量で割っていない(容量2の道なら待ちは約半分)。見積もりが重めに出る
  2. 「一度入ったゾーンには戻らない」規則は、横や後ろへの遠回りを許す限り要る。遠回りもゴールに近づく道だけにすれば要らない
- これで不要になるもの: Evictor、ReservationTable の追い出し予約、巻き戻し

## ユーザーの考え: ボトルネックから逆にたどり、ボトルネックが通せる台数しか向かわないマップを作れば解決するのでは

- 回答: 考え方は正しく、最小費用流(最大流)がやっていることと同じ。一本道なら「経路上の最小容量」を逆にたどるだけで済む
- ただし道が分かれて合流する地図では、単純な逆たどりでは足りない。合流点のボトルネックの容量を、手前の道で分け合う必要がある
  (例: start→A→C、start→B→C、C の容量1。A・B がそれぞれ1台ずつ送ると C の前に列)。
  分け合いと、ボトルネックが複数あるときの扱いを正しく計算するのが最大流の増加路
- もう一点: 台数を絞るだけでは、遠回りの道を使うか(l_i ≤ T)は決まらない。長さの比較は別に要る

## ユーザーの判断: 待ちの見積もりの対策は要る。「一度入ったゾーンに戻らない」規則は、常に全体のコストが小さくなるように進めれば要らない

- 待ちの見積もり: 前にいる台数を、その先の道が1ターンに通せる台数で割る。通せる台数は、距離の境目ごとに
  「境目を越えて入るゾーンの容量(と接続の容量)の合計」を出し、その最小を使う案を出した(最短の道だけでできた図では、
  どの道も各境目を1回だけ越えるので、これは切断の大きさになる)。queue(v) 側も同じく割る
- 戻らない規則: 「全体のコストが小さくなる」の基準が、時間で変わる見積もり(距離 + 待ち)だと、毎回小さくなっても
  待ちが変わって行き来が起きうる。変わらない値(ゴールまでの距離)が毎回小さくなる、つまり遠回りもゴールに近づく一手だけ
  (dist(v) < dist(u))にすれば、規則なしで必ず終わる
- 未決: 基準をどちらにするか(ユーザーの確認待ち)。確定したら decisions.md に記録する

## ユーザーの考え: 合流で受けきれない片方の流入は、保持マップから片方を消せばよい

- 回答: 方針としてはよい。注意点:
  1. 消すのはゾーンではなく、合流点へ入る接続(辺)。ゾーンを消すと、そこから別の道へ行く分まで失う
  2. 消す側は、ゴールまで長い方(同じなら priority でない方)
  3. 容量がちょうど割り切れないと無駄が出る(C 容量3、A・B から2ずつ → B を消すと 2 しか通らない)。
     消す代わりに「その辺は毎ターン残りの台数(ここでは1)まで」とすれば無駄が出ない。0 台が「消す」にあたる
  4. 辺を消すと、その手前のゾーンからゴールに行けなくなることがある。消したあとに距離を計算し直す
  5. ゴールに近い合流点から順に処理する(引き込みの順番と同じ)
- 未決: 消す(0/全部)か、台数の上限を付けるか。前の質問(基準を距離にするか)も確認待ち

## 質問: 接続に「毎ターン何台まで」の上限を付けるのは、保持マップ内の容量を減らす作業か

- 回答: そう。ただし
  1. 減らすのは接続の容量で、ゾーンの容量ではない(ゾーンを減らすと、すべての入口からの流入が減る)
  2. 読み込んだ Network は変えず、保持マップ側に別に持つ。TurnResolver の確認と出力・表示は元の容量で行う
  3. 意味は「その接続を合流点へ向けて毎ターン出発できる台数」。restricted への接続も課題 v2 の規則で同じ扱い
  4. 割り当てる量は、手前の道に実際に届く台数で決める必要がある(A の容量が2でも、A の手前が1台しか届けないなら
     A に2を割り当てると無駄)。ゴール側からの割り当ての前に、スタート側から「届く台数の上限」を出しておく
